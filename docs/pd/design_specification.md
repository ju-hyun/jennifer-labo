# 応答時間パーセンタイル分布分析 (Percentile Distribution / PD) 設計書

JENNIFER5 が収集した **X-View トランザクション点データ**を OpenAPI 経由で取得し、
応答時間の分布ヒストグラムとパーセンタイル指標を可視化するダッシュボードの設計書です。

[PTA](../pta/system_specification.md) と**同一の Vite マルチページアプリ (jennifer-labo) に統合**され、同じビルド・配布フローで提供されます。

- **API 仕様の根拠**: `JENNIFER5マニュアル.pdf` 付録 5.9 (OpenAPI) — 5.9.1.1〜5.9.1.3, **5.9.4.5**
- **UI 言語**: 日本語 (PTA と同一)
- **配布パス**: `/pd/`

---

## 1. プロジェクト概要

### 1.1 目的
PTA が **集計済み時系列 (dbmetrics)** を扱うのに対し、本システムは **個々のトランザクション (X-View 点データ)** を扱います。

平均値だけでは見えない **テールレイテンシ (Tail Latency)** を定量化することが目的です。
平均応答時間が 150ms でも P99 が 800ms であれば、100 人に 1 人は 5 倍以上遅い体験をしています。

- SLA / SLO 基準の策定 (例: 「P95 < 500ms」)
- チューニング前後の分布比較
- 二峰性 (bimodal) 分布の検出 — キャッシュヒット / ミスの分離など

### 1.2 成果物
- X 軸 = 応答時間 (ms) 区間、Y 軸 = トランザクション件数の **ヒストグラム**
- **パーセンタイル垂直基準線** (P50 / P90 / P99) のオーバーレイ + ラベル
- タイトルに標本数を表示: `応答時間分布 (サンプル数: 10,000 件)`

### 1.3 PTA との関係
| 区分 | PTA (既存) | PD (新規) |
| :--- | :--- | :--- |
| データソース | `/api/dbmetrics/*` | `/api/transaction/time` |
| データ単位 | 1日 / 1時間の集計値 | トランザクション 1 件 = 1 点 |
| 照会期間 | 1年 (12ヶ月チャンク) | 数分〜数時間 (**1分チャンク**) |
| 主な可視化 | 時系列ライン + ヒートマップ | 分布ヒストグラム + パーセンタイル |
| 問い | 「時間とともにどう変化したか」 | 「今このユーザ達はどんな体験をしているか」 |

両者は **JENNIFER Extension Labo** ランディング (`index.html`) 配下に並ぶ兄弟ツールです。

## 3. データアーキテクチャ

### 3.1 対象選択 API (PTA ロジック移植)

| API | パラメータ | 用途 |
| :--- | :--- | :--- |
| `GET /api/domain` | `token` | ドメインツリー (ブレッドクラム) 構築 |
| `GET /api/instance` | `token`, `domain_id` | インスタンス一覧 |
| `GET /api/business` | `token`, `domain_id` | ビジネス一覧 (`businessIndex` でインデント) |

認証トークンはクライアントに持たせず、**リバースプロキシ (本番: nginx / ローカル: Vite dev proxy) がサーバ側で注入**します (PTA §5.2 と同一)。

### 3.2 X-View トランザクション取得 API 〔付録 5.9.4.5 確定〕

```http
GET /api/transaction/time
    ?domain_id={id}
    &instance_id={id1,id2,...}     # 任意。省略時はドメイン全インスタンス
    &start_time={yyyyMMddHHmmss}
    &end_time={yyyyMMddHHmmss}
    &time_pattern=yyyyMMddHHmmss
    &token={TOKEN}                  # プロキシが注入
```

**レスポンス** (`result` 配列、1 要素 = 1 トランザクション):
```jsonc
{
  "result": [
    {
      "domainId": 7908, "domainName": "ENV-TEST",
      "instanceId": 30004, "instanceOid": 95540, "instanceName": "IBM8-T8",
      "business": [57, 54], "businessId": [57, 54], "businessName": ["B2", "T1"],
      "txid": "2936735539299047426", "guid": "",
      "clientIp": "172.17.0.1", "clientId": "-2216399679652572688", "userId": "",
      "networkTime": 0, "frontendTime": 0,
      "startTime": "20190424095930", "endTime": "20190424100002",
      "responseTime": 15900,          // ← ヒストグラムの唯一の必須フィールド (ms)
      "cpuTime": 2, "sqlTime": 1896, "fetchTime": 344, "externalcallTime": 0,
      "errorType": "",                // "" = 正常
      "applicationName": "/simula.jsp"
    }
  ]
}
```

#### 3.2.1 仕様上の重要な制約と、その帰結

| # | 仕様 (付録 5.9.4.5) | 設計上の帰結 |
| :-- | :--- | :--- |
| **C1** | 「照会時間範囲は**最大 1 分**まで」 | **1 分単位のチャンク分割が必須** (§3.3) |
| **C2** | 「X-View 基本データの照会はデータサーバに負荷を与える」 | **並列ではなく逐次実行**。チャンク間ウェイトを設定可能に |
| **C3** | `business_id` パラメータが**存在しない** | ビジネス絞り込みは**クライアント側**で `businessId[]` 配列に対して実施 (§3.5) |
| **C4** | `instance_id` は**カンマ区切りの配列**を受け付ける | 複数インスタンス選択に対応可能 (将来拡張) |
| **C5** | 件数上限・ページングのパラメータが**存在しない** | 1 分あたりの返却件数はサーバ任せ。**クライアント側で累積上限**を設ける (§3.3-3) |
| **C6** | 公式例で `start=1000, end=1001` に対し `startTime=0959` のレコードが返る | この API は**「当該区間に終了した」トランザクション**を返す。開始時刻ベースではないため、区間をまたぐ長時間 TX も漏れなく捕捉される |
| **C7** | `time_pattern` 未指定時の既定値が原文で矛盾 (表は `yyyyMMddHHmmssSSS`、備考は「unix ms」) | **常に `time_pattern=yyyyMMddHHmmss` を明示送信**して曖昧さを排除。レスポンスの `startTime`/`endTime` も同一書式で返る |
| **C8** | `start_time` / `end_time` の境界時刻を**含むかどうかの記載がない** (公式レファレンスは未確認) | 隣り合うチャンクは境界時刻を共有する (チャンク i の `end_time` = i+1 の `start_time`)。**直前のチャンクと `txid` が同じ行を除外**する (`dropBoundaryDuplicates()`)。境界が排他的なら重複は起きず、両側を含む仕様でも二重計上しない。除外件数は画面に通知。**観測 (2026-11-04、実サーバでの照会)**: 重複の通知は表示されず、境界は排他的である可能性が高い。ただし重複は境界時刻のミリ秒まで一致するトランザクションがある場合にしか生じず、トラフィックの少ないドメインでは包含仕様でも観測されないため**確定ではない**。正常な行は消さないので防御処理は維持する |

### 3.3 1分チャンク逐次収集エンジン

```
照会期間  10:00:00 ─────────────────────────────────► 10:05:00
チャンク  [10:00-10:01][10:01-10:02][10:02-10:03][10:03-10:04][10:04-10:05]
             ①逐次        ②逐次        ③逐次        ④逐次        ⑤逐次
             ↓            ↓            ↓            ↓            ↓
          responseTime を Float64Array に追記 → 進捗バー更新 → 中間描画
```

1. **チャンク生成**: 照会期間を 1 分ごとに区切った配列 (`[t, t+1min]`) を生成。隣り合うチャンクは境界の時刻を共有する (C8)。
   - 端数は 1 分に丸めるのではなく、最後のチャンクのみ実際の終了時刻を使用 (例: 10:04:00〜10:04:30)。
2. **逐次実行**: `for...of` + `await` で 1 件ずつ。**同時実行数 = 1**。
   - チャンク間ウェイト (既定 `0ms`、設定で 0〜500ms) — データサーバ負荷が問題になる環境向け。
   - 失敗チャンクは最大 2 回リトライ (指数バックオフ 300ms / 900ms)。それでも失敗したら
     **そのチャンクだけスキップして続行**し、完了時に「N/M チャンク失敗」を警告表示。
   - **境界の重複除去** (C8): 直前のチャンクの `txid` だけを保持して比較する (メモリはチャンク 1 つ分)。
     失敗したチャンクの直後は比較対象がないため、保持をリセットする。
3. **ストリーミング蓄積**: レスポンス全件をオブジェクトのまま保持しない。
   - `responseTime` を **`Float64Array`** に追記 (初期容量 65,536、満杯時に倍化)
   - 詳細パネルは、クリックした区間の行を**応答時間の降順で上位 200 件**だけオブジェクトに復元して表示
     (区間全体をオブジェクト化しない)
   - `applicationName` 別の集計は Map で逐次更新
4. **安全上限**: 累積件数が `MAX_POINTS` (既定 **300,000**) を超えたら収集を中断し、
   `標本上限に到達しました。期間を狭めてください` を警告表示。既収集分でチャートは正常描画。
5. **進捗と中断**: `データロード中... (23/60 チャンク · 48,120 件)` を進捗バーで表示。
   **中断ボタン**でその時点までのデータで確定描画。
6. **インクリメンタル描画**: 1 秒に 1 回を上限としてヒストグラムを再描画し、
   長時間の収集でも進行が目に見えるようにする。

> **想定コスト**: 1 分あたり 300ms の応答として、1 時間照会 = 60 チャンク ≒ 20 秒。
> 既定の期間プリセットは `直近5分` / `直近15分` / `直近30分` / `直近1時間` とし、
> プリセットは「照会」ボタンを押した時点の現在時刻で期間を取り直します (画面を開いたままでも古い区間を照会しない)。
> チャンク数バッジは 60 を超えると警告色になり、`CONFIRM_CHUNKS` (既定 120) を超える指定は
> 実行前に「N 回の逐次照会になります」と確認ダイアログを出します。

### 3.4 パーセンタイル算出

- **方式**: 正確算出 (exact)。`Float64Array` を昇順ソート後、**線形補間**方式。
  ```
  idx = (N - 1) * p / 100
  lo = floor(idx), hi = ceil(idx)
  Pp = v[lo] + (v[hi] - v[lo]) * (idx - lo)
  ```
  ビン近似は P99 のようなテール側で誤差が大きくなるため採用しません。
- `Float64Array.prototype.sort()` は数値ソートが既定。30 万件で 100ms 前後。
- **算出指標**: P50 / P75 / P90 / P95 / P99 / P99.9、平均、最小、最大、標準偏差、標本数、エラー率。
- **チャート既定表示**: P50 / P90 / P99 (トグルで個別 On/Off)。

### 3.5 クライアント側フィルタ (制約 C3 への対応)

API がビジネス絞り込みに対応しないため、**収集済みデータに対してクライアント側で適用**します。
再照会は発生せず、即座に再計算されます。

| フィルタ | 対象フィールド | 備考 |
| :--- | :--- | :--- |
| ビジネス | `businessId[]` に選択 ID が含まれるか | 配列なので `includes` 判定 |
| インスタンス | `instanceId` | API 側でも絞れるが、収集後の切り替えを高速化するため両対応 |
| エラー | `errorType !== ""` | 正常のみ / エラーのみ / 全件 |
| アプリケーション | `applicationName` 部分一致 | インクリメンタルサーチ |
| 応答時間レンジ | `responseTime` | ヒストグラムのドラッグ選択と連動 |

> フィルタ適用時はヒストグラム・パーセンタイル・サマリカード・CDF をすべて再計算します。
> 元データ (生オブジェクトのサンプル + 全件の `responseTime`) は保持しているため、再照会不要です。

### 3.6 ヒストグラム区間 (Bin) 設計

応答時間分布は「左に密集し右へ長い裾を引く」形状になるため、以下の規則で可読性を確保します。

- **既定 — 自動等間隔 (Auto Linear, ビン幅 50ms 固定)**
  - 表示上限 `xMax` = `P99.5` を「きりの良い数」(1/2/5 × 10ⁿ) に切り上げ
    - 例: P99.5 = 963ms → `xMax = 1,000ms`
  - ビン幅 = `50ms` 固定 (X 軸目盛り間隔と一致)。`xMax` は P99.5 を 50ms の倍数へ切り上げ
  - ビン数が 240 を超える場合のみ、ビン幅を 50ms の倍数へ広げる
  - **上限超過分は最終ビンに合算 (クリッピング)** し、`1,000ms+` ラベルとオレンジ色を付与
    - 参照画像の右端で突出している棒がこのオーバーフロービンに相当
- **ログビン (Log Bin)**: 1ms〜60s のようにレンジが 3 桁以上開く環境向けのトグル
- **手動 (Manual)**: `ビン幅` / `X軸上限` を直接指定して固定 — チューニング前後比較で軸を揃えるために必須

## 5. 主要コンポーネント

### 5.1 フィルタ領域
- **階層型ドメインブレッドクラム**: PTA の `groupHierarchy` ツリー + ポップオーバー UI を移植
- **対象切替ラジオ**: インスタンス / ビジネス (PTA 同一)
  - インスタンス選択 → API の `instance_id` に反映 (サーバ側で絞り込み)
  - ビジネス選択 → クライアント側フィルタ (§3.5、制約 C3)
- **期間選択**: プリセット (`直近5分` / `直近15分` / `直近30分` / `直近1時間`) + `datetime-local` カスタム
  - 期間からチャンク数を即時計算し `→ 60 チャンク` とバッジ表示
- **照会ボタン**: PTA は自動再照会だが、本システムは**明示的な照会ボタン**
  (X-View の逐次照会をセレクタ操作のたびに発火させないため)

### 5.2 サマリカード
件数 / 平均 / P50 / P90 / P95 / P99 / 最大 / エラー率 の 8 枚。
比較モード (§6.4) 有効時は前回照会との差分 (Δ) を併記。

### 5.3 メインヒストグラム
- Chart.js `bar`、`categoryPercentage: 1.0` / `barPercentage: 1.0` で棒間の隙間を排除 (参照画像準拠)
- **パーセンタイル オーバーレイプラグイン**: `afterDatasetsDraw` でキャンバスに垂直線 + ラベルを直接描画
  - ラベルは参照画像同様に **縦書き (rotate -90°)**、重なる場合は自動でオフセット
- **ツールチップ**: `150 〜 175ms : 1,102件 (11.02% / 累計 68.4%)` — 区間比率と**累積比率 (CDF)** を併記
- **Y軸ログトグル**: テール側の低い棒を視認するため線形/ログを切替

### 5.4 詳細スライドパネル
PTA のスライドインオーバーレイを継承。
- ヒストグラムの棒クリック → その応答時間区間のトランザクション (最大 200 件) を左パネルに表示
- 列: 時刻 / アプリケーション / 応答時間 / インスタンス / CPU / SQL / エラー
- 応答時間の降順、インライン横棒で相対比較。行ホバーでフィードバック
- パネル表示中はメインチャートの操作をロック、`ESC` で閉じる (PTA 同一)

### 5.5 パーセンタイル曲線 (CDF)
X 軸 = パーセンタイル (0〜100、90 以上を拡大する補助軸)、Y 軸 = 応答時間 (ms)。
「P99 以降で急激に立ち上がる崖 (cliff)」の有無でテール遅延の深刻度を判別します。

### 5.6 アプリケーション別 P99 ランキング
`applicationName` でグルーピングし P99 上位 10 件を横棒表示。
棒クリックで当該アプリのみに絞り込み (ドリルダウン)。

## 6. ユーザインタラクション

1. **収集進捗**: `データロード中... (23/60 チャンク · 48,120 件)` + 進捗バー。**中断ボタン**あり
2. **パーセンタイルトグル**: P50/P75/P90/P95/P99/P99.9 の個別 On/Off
3. **クライアントサイドフィルタ** (§3.5): 再照会なしで即時再計算
4. **比較モード (Overlay Compare)**: 直前の照会結果をスナップショットとして保持し、現在の分布に半透明で重畳
   - チューニング前後 / 昨日と今日の比較用。軸 (ビン幅・上限) は自動で固定同期
5. **ESC**: 詳細パネルを閉じる / ドリルダウン解除
6. **ポップアップヘルプ**: `pd/help.html` を `window.open` で表示 (PTA 方式継承)
   - パーセンタイルの概念、「平均の罠」、二峰性分布の読み方、オーバーフロービンの意味
   - セクション別 `?` ボタンが該当アンカー (`#histogram`, `#cdf`) にジャンプ
7. **CSV エクスポート**: ビン別集計表とパーセンタイル要約を CSV 保存

## 8. ビルドと配布

### 8.1 Vite MPA (PTA と統合)
- `rollupOptions.input` は PTA と共通の 5 エントリ: `main(index.html)`, `pta(pta/index.html)`, `pta-help(pta/help.html)`, `pd(pd/index.html)`, `pd-help(pd/help.html)`
- アセット出力: PD は `dist/pd/asserts/`、PTA は `dist/pta/asserts/`、両アプリ共有チャンク (chart.js 等) は `dist/shared/asserts/`
- ビルド後 `fix-paths.js` が `dist/pd/*.html` (および `dist/pta/*.html`) の `../pd/asserts/` → `./asserts/` に補正

### 8.2 開発サーバ
- ポート **5177** (PTA・PD 共通の単一ポート、`strictPort: true`。旧 PD 専用の 5178 は廃止)
- `/api` → `https://demo.jennifersoft.co.jp/` にプロキシ (`vite.config.js` の `target`)、`secure: true` (既定。自己署名証明書のサーバで開発する場合のみ `DEV_INSECURE_TLS=1`)。開発サーバは既定で `localhost` のみにバインド (`DEV_HOST` で変更)
- `proxyReq` フックで `.env` の `DEV_API_TOKEN` を `token` クエリに注入
- `proxyRes` フックで CORS 関連ヘッダを注入 (PTA と共通の設定)

### 8.3 本番配布 (nginx)
[DEPLOY_GUIDE_NGINX.md](../DEPLOY_GUIDE_NGINX.md) (共通ガイド) 参照。
- `dist/` 全体 (ランディング + `pta/` + `pd/` + `shared/`) を一括配布し、`location /` 静的配信 + 許可リスト方式の `/api/` プロキシでサーバ側からトークンを注入 (`map` + `set $args`)。HTTPS / Basic 認証 / GET 限定 / `transaction/time` のレート制限を併用
- `/pta/`, `/pd/` は同一 `dist` に含まれ、`/api/` プロキシも共有

## 9. リスクと対応

| リスク | 影響 | 対応 |
| :--- | :--- | :--- |
| データサーバへの負荷 (仕様で明示的に警告) | 運用影響 | 逐次実行 (同時数 1)、チャンク間ウェイト設定、期間プリセットで過大照会を抑制 |
| 長期間照会でチャンク数が膨大 | 待機時間増 | チャンク数バッジで事前提示、進捗バー + 中断ボタン、インクリメンタル描画 |
| 1 分あたりの件数が想定外に多い | ブラウザ停止 | `Float64Array` + `MAX_POINTS` 上限 (§3.3-4) |
| 一部チャンクの失敗 | 分布の欠損 | 2 回リトライ後スキップして続行、失敗チャンク数を明示 |
| ロングテールでヒストグラムが潰れる | 判読不能 | オーバーフロービン + Y軸ログトグル + ログビンモード (§3.6) |
| 標本が少ない区間の P99 の信頼性 | 誤判断 | 標本数 < 1,000 で「標本不足」バッジを表示 |
