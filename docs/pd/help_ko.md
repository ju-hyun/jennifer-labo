# 분석 가이드 (한국어 대역)

> `pd/help.html` (일본어)의 한국어 대역본. 사내 검토용이며 화면에는 노출되지 않는다.
> 원문은 [help_ja.md](./help_ja.md).

## 1. 시스템 개요

JENNIFER5 가 수집한 **X-View 트랜잭션 점 데이터**를 OpenAPI 로 가져와 응답시간의 **분포**를 시각화한다.
집계된 평균값을 다루는 PTA 와 달리, 개별 트랜잭션 1건을 1개의 점으로 취급한다.

### 평균값으로는 왜 부족한가

평균 응답시간 150ms 인 시스템이라도 P99 가 800ms 라면 **100 요청 중 1회는 5배 이상 느린 경험**이 발생한다.
평균값은 분포의 꼬리를 가리므로 실제 사용자 경험을 대표하지 못한다. SLA/SLO 는 평균이 아니라 백분위로 정의해야 한다.

### 데이터 수집 방식

`/api/transaction/time` 은 **1회 조회 최대 1분**이라는 제약이 있어(부록 5.9.4.5),
지정 기간을 1분 단위 청크로 나눠 **순차(동시 실행 수 1)** 로 수집한다.
매뉴얼이 「X-View 조회는 데이터서버에 부하를 준다」고 명시하고 있어 의도적으로 병렬화하지 않는다.

「직근 N분」 프리셋은 **「照会」 버튼을 누른 시점의 현재 시각**으로 기간을 다시 계산한다
(화면을 열어 둔 채 시간이 지나도 오래된 구간을 조회하지 않는다). 조회 횟수가 120회(=120분)를 넘으면
실행 전에 확인 대화상자를 띄운다 (`config.js` 의 `CONFIRM_CHUNKS` 로 변경).

인접한 청크는 경계 시각을 공유한다. API 가 경계 시각을 양쪽에서 포함하면 경계에서 종료한 트랜잭션이
2번 반환될 수 있으므로, 직전 청크와 `txid` 가 같은 행은 자동으로 제외하고 제외한 건수를 화면에 알린다.

### 대상 필터링

| 필터 | 실행 위치 | 이유 |
| :--- | :--- | :--- |
| 도메인 | API | `domain_id` 는 필수 파라미터 |
| 인스턴스 | API | `instance_id` 파라미터 지원 |
| 비즈니스 | 클라이언트 | API 에 해당 파라미터가 없어 `businessId` 배열로 판정 |
| 에러 / 앱 이름 | 클라이언트 | 재조회 없이 즉시 재계산 |

## 2. 메인 히스토그램

### 분포 형태 읽기

| 형태 | 의미 | 다음 액션 |
| :--- | :--- | :--- |
| 왼쪽 급경사 + 오른쪽 롱테일 | 정상적인 Web 시스템의 전형 | 꼬리의 원인(GC/락/느린 SQL) 특정 |
| 봉우리 2개(이중봉) | 두 종류의 처리가 혼재 | 앱 이름으로 좁혀 봉우리 분리 |
| 전체적으로 평평하고 넓음 | 응답시간이 불안정 | PTA 로 같은 시각의 CPU·TPS 확인 |
| 특정 값에 뾰족한 스파이크 | 타임아웃 설정값·외부연동 고정 대기 | 해당 구간 막대 클릭해 개별 확인 |

### 백분위 기준선

- **P50(중앙값)** — 절반의 사용자가 이보다 빠름. 「전형적인 경험」
- **P90** — 10 요청 중 1회는 이보다 느림
- **P99** — 100 요청 중 1회. 한 화면이 20개 리소스를 읽으면 화면 단위로는 약 20% 가 P99 를 밟는다

평균값은 분포 안에 선으로 나타나지 않는다. 평균과 P50 이 크게 벌어져 있다면
그 자체가 「극단적으로 느린 일부가 평균을 끌어올리고 있다」는 증거다.

### 오버플로 빈(주황 막대)

X축 상한은 P99.5 기준으로 자동 결정하며, 상한 초과분은 **최종 빈에 합산**해 주황색으로 표시한다.

### 빈 모드와 Y축 로그

- **자동(등간격)** — 기본. P99.5 를 상한으로 약 40개 빈
- **로그 스케일** — 레인지가 3자릿수 이상 벌어질 때
- **수동** — 튜닝 전후 비교 시에는 반드시 수동으로 축을 맞출 것
- **Y축 로그** — 꼬리 쪽의 낮은 막대를 보이게 함

## 3. 백분위 곡선(CDF)

- **완만한 우상향** — 응답시간 안정, 꼬리 리스크 낮음
- **P99 부근에서 급격히 솟는 「절벽」** — 타임아웃, 재시도, GC Stop-the-world 가 전형

## 4. 애플리케이션별 P99 TOP10

`applicationName` 별 P99 상위 10건. 막대 클릭 시 드릴다운(애플리케이션 이름 **완전 일치**), `ESC` 로 해제.
「애플리케이션」 입력란 필터는 **부분 일치**다 (예: `/api/user` 는 `/api/user/profile` 도 포함).
표본 5건 이상인 애플리케이션만 대상.

## 5. FAQ

**조회가 오래 걸린다** — 1시간 조회 = 60회 API 호출. 120회를 넘으면 실행 전 확인창이 뜬다. 청크 수 배지를 참고하고 「중단」으로 중간 확정 가능.

**「표본 상한 도달」** — 누적 30만 건에서 중단 (`config.js` 의 `MAX_POINTS`).

**「표본 부족」** — 1,000건 미만이면 P99 가 몇 건의 관측값으로 결정되어 신뢰성이 낮다.

**일부 청크 실패** — 2회 재시도 후 스킵. 빈발하면 `CHUNK_WAIT_MS` 를 100~500 으로 설정.

**「JENNIFERサーバに接続できませんでした」 표시** — 모든 청크 취득에 실패한 상태. 네트워크와 API 프록시(토큰 포함)를 확인한다.
운영 환경에서는 더미 데이터를 표시하지 않는다 (실데이터로 오인하지 않도록). 개발 서버(`npm run dev`)에서만 확인용 모크 데이터를 표시하고 경고한다.

**「取得済みの N 件のみを表示しています (不完全なデータです)」 표시** — 수집 도중 인증 오류(401) 등이 발생한 경우.
이미 받은 실데이터는 버리지 않고 표시하지만 기간 일부가 비어 있으므로 건수의 절대값이 아닌 형태의 경향으로 본다.

**「チャンク境界で重複していた N 件を除外しました」 표시** — 이상이 아니다. API 가 경계 시각을 양쪽에서 포함해 반환해
같은 `txid` 가 인접한 2개 청크에 나타났고, 중복분을 제외했다는 알림이다.

**지정한 시작 시각 이전 트랜잭션이 포함된다** — 사양대로다. 이 API 는 **해당 구간에 종료한**
트랜잭션을 반환하므로 구간을 걸친 장시간 TX 도 누락 없이 잡힌다.
